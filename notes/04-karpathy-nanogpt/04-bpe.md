## 1. 先说清楚 BPE 在干什么

一句话版本：

> **BPE 做的是无损压缩——把一段文本写成尽可能少的 token，而词表大小是有预算的。**

**为什么"预算"这个词是认真的。** 每往词表里加一个 token，`wte`（token 嵌入表）就多一行、`lm_head`（输出头）就多一列。§7 会看到，词表从 87 涨到 587，参数量跟着涨了 96,500。所以每一个名额都得花在刀刃上。

**那怎么花？** 看一个具体的选择。假设语料里到处是 `... t h e ...` 这样的字符序列，现在手里有一个名额，可以合并任意一对相邻符号：

- 合并 `t` + `h`：全文每一处都省下 1 个符号 → 收益 ≈ `th` 出现的次数
- 合并 `q` + `z`（如果几乎不出现）：收益 ≈ 0

所以准则就出来了：

> **合并「出现次数最多的那一对」——一个名额换来的收益最大。**

这就是 BPE 全部的贪心准则。注意它**不算"信息量"，它只是数频率**——频率是"能省多少"的廉价代理。一对出现 $N$ 次，合并它就让序列短大约 $N$ 个符号。

**这个准则的效果，可以直接量出来。** 压缩后每个 token 平均装 **2.87 个字符**（§4 算）。那么：

- 总信息量不变（还是同一段文本）
- token 数降到 0.3479 倍
- 所以**每个 token 承载的信息必然涨**

用模型自己的 loss 来量（loss = 平均每个 token 的"意外程度"，单位是 nats，§6 会解释为什么它能当"信息量"用）：

| | bit / token | token 数 | 全文总计 |
|---|---|---|---|
| 字符级 | 2.2327 | 2,000,000 | 4.465 Mbit |
| BPE | **4.8671** | 695,855 | **3.387 Mbit** |

（"全文总计" = bit/token × token 数，也就是把 val loss 当作平均编码成本折算出整段文本的开销。）

**每个 token 装的从 2.23 bit 涨到 4.87 bit，而全文的总开销反而降了 24%。** 这就是"压缩"两个字的确切含义，也是这一篇的主线：

> 压缩 = **每个 token 装更多** × **token 更少**。两个方向同时改善。

请记住这张表。§5 那个"BPE 的 loss 怎么反而更高"的疑问，答案就在它的左半边——**loss 变高是设计目标，不是副作用。**

## 2. 具体怎么实现：一个循环，三个细节

去掉所有细节，训练就是一个五步循环：

```
1. 把文本切成词，每个词拆成字符序列
2. 数一数：所有相邻的符号对里，哪一对出现最多？
3. 把那一对合并成一个新符号，加进词表
4. 全文所有词里，都执行这个合并
5. 回到第 2 步，重复 N 次（N = 你想要的合并次数）
```

500 次循环之后，词表 = 87 个原始字符 + 500 个合并出来的新符号 = **587**。每个新符号都对应一步"当时最省的那一刀"。

循环本身说完了。剩下三个细节，决定了它能不能真用起来。

**细节 ①：预分词——把输入从「字符序列」换成「词典」。**

这是整个 BPE 里最容易被误解的一步。它**不是为了方便人读**，它是**换掉了算法迭代的对象**：从 200 万个字符，换成 15,407 条「词: 次数」。

先看一个能一眼看穿的例子。假设语料就是 `" the cat"` 重复 20 万次（注意前导空格——写成 `"the cat "` 会在词典里多出两条边界残渣，反而看不清）：

**不预分词**，输入是一个 160 万长度的字符序列，每轮要沿它走一遍：

```
' ','t','h','e',' ','c','a','t',' ','t','h','e', ...
→ 数一遍相邻对 ≈ 1,599,999 次操作
```

**预分词之后**，输入变成一个词典，只需沿 2 条记录走一遍：

```
{' the': 200000, ' cat': 200000}
→ ' the' 有 3 个相邻对、' cat' 有 3 个，各乘 200000  ≈ 6 次操作
```

**160 万次 vs 6 次——差 26 万倍。** 差在哪？不预分词时，一个词出现 20 万次，那 20 万个位置**每一个都得单独扫**；预分词把它折叠成「1 条记录 + 一个数字 200000」——**扫一遍，然后乘回去**。

这就是提取公因式。等价的说法：版图上有 100 万个标准单元实例，网表里只存「200 种单元类型 + 各用了几次」——你不会仿真 100 万个副本，你仿真 1 个再乘 100 万。

代码里就是这一行（**这行之后，那 200 万个字符再也没被碰过**）：

```python
freq = Counter(pre_split(text))       # 文本 -> 「词: 次数」词典
parts = {w: tuple(w) for w in freq}   # 之后所有统计都在这 15,407 条上做

pairs = Counter()
for w, f in freq.items():
    s = parts[w]
    for pair in zip(s, s[1:]):
        pairs[pair] += f              # 每个词只数一次，乘以它的次数
```

真实语料上：**2,000,000 个字符，切出 401,025 个词，其中只有 15,407 个是不同的**——平均每个词重复 26 次。这 15,407 条记录一共占 115,043 个符号，所以每轮只需扫 11.5 万个符号，剩下的 26 倍靠「乘以次数」补回来。500 次合并因此只要 **15.4 秒**。

语料越大越划算：文本长度无限涨，不同的词数涨得很慢（5 万字符时 1,738 个，40 万字符时才 6,288 个）。40 GB 语料上，不按词统计的 BPE 根本跑不完。

**但这一步不是白拿的。** 按词统计意味着跨词边界的对（`'e '`、`'ed t'`）**根本不在统计范围内**，永远选不上——等于人为禁止了它们，压缩率因此受损。实测（**20 万字符**语料、500 次合并，验证段是另外 20 万字符）：

| | 每轮扫多少符号 | 每轮配对次数 | 训练耗时 | 验证段 token 数 |
|---|---|---|---|---|
| 不预分词（纯字符流）| 200,000 | 199,999 | 15.6 秒 | 67,967 |
| 预分词 | 29,144（4,248 个词）| 24,896（**少 8 倍**）| 3.8 秒 | 68,478（**多 0.75%**）|

**用 0.75% 的压缩率，换每轮少 8 倍的统计量——这笔交易显然划算。**（语料越大差距越大：全量 200 万字符上，配对次数是 1,999,999 vs 99,636，少 20 倍。）

（注意两点：一是"禁止跨词合并"**不是另一个独立决定**，它就是"按词统计"的自动副产品；二是端到端只快约 4 倍、远没有 8 倍那么夸张，因为"合并规则"那一步仍要扫全序列。但差距随语料拉大：5 万字符约 3 倍，40 万字符约 6 倍。）

**细节 ②：空格要粘在词上——把切词丢掉的空白补回来。**

预分词本身会**制造**一个问题：文本被切成词，空格就丢了。解码时再也分不清原来是 `" "`、`"  "` 还是换行——**你没法在解码时"猜"出正确的空白**。

解决办法是把前导空格粘到后面的词上：

```python
SPLIT = re.compile(r' ?[^\s]+|\s+')
```

于是 `" Once"` 和 `"once"` 是两个不同的词，空格成了 token 的一部分。**解码变成纯拼接，不补任何东西就是原文，天然无损。**（实测核对过：预分词版和纯字符流版，解码结果都与原文逐字符相同。）

附带的好处：BPE 于是能学到 `' the'`（词首形态）和 `'the'`（词中形态）是两个不同的 token——500 条规则里有 **294 条（59%）**以空格开头，正是这一类。

**细节 ③：编码新文本时，是"重放"合并顺序，不是搜索最优切分。**

训练产出的是一张**有序**规则表——第 $i$ 条就是第 $i$ 步合并的那一对。给一个新词编码，就按这个顺序来：

```
在一个词内部，反复找出「优先级最高、且当前确实存在」的那一对，合并它，直到没有可合并的
```

注意这里**没有**去找"哪种切法 token 最少"。BPE 不优化切分，它只是把训练时的合并顺序重放一遍——**因为顺序是固定的，切分结果就是唯一确定的**，又便宜又可复现。这是设计上的一次取舍：放弃了最优切分，换来了 $O(\text{词长})$ 的编码。

效果：

```
' Once upon a time'  字符级 17 个 token  ->  BPE 5 个
                    ' ' │ 'Once' │ ' upon' │ ' a' │ ' time'
```

**这个"便宜"是可以量的。** 把 20 万字符分别交给两个分词器编码：**A 0.1 秒，B 7.6 秒——A 快 80 倍以上。**

差在哪：A 的处理单位是**词**，同一个词只编码一次，之后全是查表；B 没有"词"这个单位可以缓存，只能对着整条字符序列把 500 条规则重放一遍。**所以预分词买到的第三样东西，是给编码解锁了一层缓存。**

## 3. 这 500 条规则，就是一部英文词法

前 25 条（优先级从高到低）：

```
  0.  'h' + 'e'   -> 'he'        9.  ' t' + 'o'  -> ' to'      18.  ' ' + 'he' -> ' he'
  1.  ' ' + 't'   -> ' t'       10.  ' ' + 'b'   -> ' b'       19.  ' ' + 'l'  -> ' l'
  2.  ' ' + 'a'   -> ' a'       11.  'i' + 'n'   -> 'in'       20.  ' wa' + 's' -> ' was'
  3.  ' ' + 's'   -> ' s'       12.  ' ' + 'h'   -> ' h'       21.  'e' + 'r'   -> 'er'
  4.  ' ' + 'w'   -> ' w'       13.  ' w' + 'a'  -> ' wa'      22.  ' ' + 'c'   -> ' c'
  5.  'n' + 'd'   -> 'nd'       14.  'r' + 'e'   -> 're'       23.  ' ' + 'd'   -> ' d'
  6.  ' t' + 'he' -> ' the'     15.  'i' + 't'   -> 'it'       24.  ' ' + 'p'   -> ' p'
  7.  'e' + 'd'   -> 'ed'       16.  ' ' + 'f'   -> ' f'
  8.  ' a' + 'nd' -> ' and'     17.  'o' + 'u'   -> 'ou'
```

它**不是**按语言学设计的，是按使用频率长出来的：先有字母对（`he`、`nd`、`ed`），再有带空格的词首形态（` t`、` a`），再把常见的短词整个拼出来（` the`、` and`、` was`）。再往后越排越具体：

| 目标 token | 第几位合并产生 |
|---|---|
| `' the'` | 6 |
| `' and'` | 8 |
| `'ing'` | 28 |
| `<\|endoftext\|>` | **122** |
| `' little'` | 132 |
| `'ly'` | 153 |
| `'Lily'` | 355 |

注意第 122 行那个——**分隔符比单词 `' little'` 还早拼出来。** 它是什么，下面说。

还有一条能看出细节 ① 生效了：**500 条里有 294 条（59%）以空格开头**——正是「词首形态」那一类。

**它自己"发现"了一个特殊符号：`<|endoftext|>`。**

TinyStories 是一篇篇故事拼起来的，故事之间用 `<|endoftext|>` 隔开：

```
...they played together all day and became best friends.
<|endoftext|>
Once upon a time, in a big...
```

前 200 万字符里它出现 **2,387 次**（平均每 838 字符一次，正好一篇一次）。**没有任何代码告诉 BPE 这是个特殊符号**——对它来说，这只是一个出现了 2,387 次的 13 字符序列，在 15,407 个不同的词里频率**排第 22**，比 `' her'`、`' he'`、`' she'` 都高。

于是它被当成普通高频序列，一步步拼了出来：

```
116. '<'            + '|'   -> '<|'
117. '<|'           + 'end' -> '<|end'
118. '<|end'        + 'o'   -> '<|endo'
119. '<|endo'       + 'ft'  -> '<|endoft'
120. '<|endoft'     + 'ext' -> '<|endoftext'
121. '<|endoftext'  + '|'   -> '<|endoftext|'
122. '<|endoftext|' + '>'   -> '<|endoftext|>'
```

**七次连续合并（第 116~122 条），全用在它身上。** 而零件是从普通英文里白捡的：`'nd'`（第 5 条）随即被第 8 条用来拼出 `' and'`，`'end'`（第 55 条）来自 `friend` 这类词，`'ext'`（第 108 条）来自 `next`。**为英文单词学的碎片，被复用到了分隔符上。**

结果：字符级要 **13 个 token** 才写得出来的东西，BPE **1 个**就够。

> GPT-2 是**手工注册**这个特殊 token 的（编号 50256）。这里没有手工——它是从频率里自己长出来的。

## 4. 同一段文本，token 数降到 1/3

| | 词表 | 2,000,000 个字符 → | token / 字符 |
|---|---|---|---|
| 字符级 | 87 | 2,000,000 个 token | 1.0000 |
| BPE | 587 | **695,855 个 token** | **0.3479** |

**压缩 2.87 倍。** 落到具体的词上：

| 文本 | 字符级 | BPE | BPE 的切法 |
|---|---|---|---|
| `' the'` | 4 | **1** | `' the'` |
| `' little'` | 7 | **1** | `' little'` |
| `' mouse'` | 6 | 3 | `' m' │ 'ou' │ 'se'` |
| `' Once upon a time'` | 17 | **5** | `' ' │ 'Once' │ ' upon' │ ' a' │ ' time'` |

最直接的收益在 `block_size`：

$$\text{字符级：} 50 \text{ token} = 50 \text{ 个字符} \qquad \text{BPE：} 50 \text{ token} = 143.7 \text{ 个字符}$$

**同一个 `block_size = 50`，模型一次能看到的文本多了近 3 倍。** 注意力是 $O(T^2)$ 的，扩大上下文要么付平方代价、要么换分词器——这就是「换分词器」被挣出来的地方。

## 5. 为什么 BPE 的 loss 一定更高

跑完 1500 步，两组 val loss 摆在面前：

| | val loss | 困惑度 $= e^{\text{loss}}$ |
|---|---|---|
| 字符级 @1500 | **1.5476** | 4.70 |
| BPE @1500 | **3.3736** | 29.18 |

第一反应一定是「BPE 差了一倍多，困惑度差了 6 倍，换亏了」。

**回到 §1 那张表：BPE 每个 token 要装 4.87 bit，字符级只装 2.23 bit。** 要装的信息多了一倍多，loss 当然高一倍多——**这不是 BPE 变差了，这是 §1 那条设计目标的直接读数。**

换个说法就更容易接受：字符级每步只需要预测 1 个字符，BPE 每步要预测平均 2.87 个字符那么大的块。**拿 4.70 和 29.18 比，等于拿"猜一个字母"和"猜三个字母"比正确率。**

> **loss 和困惑度都是「每 token」的量，只在分词器相同时可比。**

顺带一个佐证：如果 BPE 只是把 2.87 个字符随便粘在一起，它的 loss 应该正好是字符级的 2.87 倍，也就是 $2.87 \times 1.5476 \approx 4.44$ nats。实测是 **3.37**，明显更低。**说明 BPE 挑出来的确实是"好猜的高频块"，而不是随手切的。**（这是粗算：把字符级的 per-char loss 当成每字符的不确定度。）

## 6. 换到能比的尺子：每字符多少 bit

分词器无关的量是：**编码原文的每个字符，平均需要多少比特。** 叫 BPC（bits per character，每字符比特数）。

loss 是以 e 为底的对数（写作 **ln**，单位 nats）。先换成比特，再折算到每个字符：

$$\text{BPC} = \underbrace{\frac{\text{loss}}{\ln 2}}_{\text{每 token 多少 bit}} \times \underbrace{\frac{\text{token 数}}{\text{字符数}}}_{\text{每个字符几个 token}}$$

字符级的第二个因子恰好是 1.0，BPE 是 0.3479。代进去：

| 实验 | val loss | bit / token | token / 字符 | **BPC** |
|---|---|---|---|---|
| 字符级 @1500 | 1.5476 | 2.2327 | 1.0000 | 2.2327 |
| 字符级 @6000 | 1.2610 | 1.8192 | 1.0000 | 1.8192 |
| BPE @1500 | 3.3736 | 4.8671 | 0.3479 | **1.6933** |
| BPE @6000 | 2.8472 | 4.1077 | 0.3479 | **1.4290** |

结论完全反过来：

- 同样 1500 步，BPE 把每字符成本从 2.2327 bit 降到 1.6933 bit，**少 24.2%**（正好是 §1 那张表里 4.465 Mbit → 3.387 Mbit 的降幅）
- 更扎眼的是这一行：**BPE 跑 1500 步（1.6933）比字符级跑 6000 步（1.8192）还好，少 6.9%**——用四分之一的算力

> 顺便解释了为什么现在的论文大多报 **BPB**（bits per byte，每字节比特数）而不是困惑度：**模型换了分词器，困惑度就没法比了，BPC / BPB 不会。**

**而代码里没有任何一行告诉它要这么做。** 没插入 EOS 字符、没加 `break`、`generate` 还是数满 500 步就停。它学会这件事，只因为 `<|endoftext|>` 在语料里出现了 2,387 次。

密度也对得上：这次新生成 **1,469 字符**，按语料密度（每 838 字符一次）应该出现约 1.75 次，实际出现 1 次。

作为对照：在 1 KB 的内置语料上实测过，手工插入 EOS 字符重训，**在真正的段落边界，模型给的 EOS 概率最高只有 0.0047**——学不会。**同一个任务，语料一大，一行代码没改就自己学会了。**

沿用笔记 03 的那把尺子（把生成文本按字母切词，看有多少是语料里真出现过的词）：

| | 生成词数 | 真词 | **真词率** |
|---|---|---|---|
| 字符级 @1500 | 104 | 61 | **58.7%** |
| BPE @1500 | 312 | 266 | **85.3%** |
| BPE @6000 | 284 | 268 | **94.4%** |

BPE @6000 的假词只剩 16 个（`growlin`、`operature`、`outswer` 这种），而且**段落、对话、成对引号全都出来了**。

两笔诚实的账：

- **模型变大了。** 参数 357,303 → **453,803**，多 96,500。来源只有两处，都在词表上：`wte` 8,352 → 56,352（+48,000），`lm_head` 8,439 → 56,939（+48,500）。架构一个零件没动。（这就是 §1 说的"词表是预算"。）
- **每步看到的文本多了 2.87 倍。** 1500 步 = 2,400,000 个 token，字符级是 1.2 遍数据，BPE 是 **3.45 遍**。这不是 bug——**"同样的算力看到更多文本"正是换分词器的收益本身**。

还有一点别忘了：BPE 的输出层要从 587 个选项里挑，字符级只从 87 个里挑。**BPE 玩的是一场更难的输出游戏，还赢了。**

## 8. 现在它能自己停下来了

§7 那段生成里，模型输出了 `<|endoftext|>` 之后**接着讲了下一篇**，一直讲到预算用完、句子断在 `a paving` 中间才停。因为 `generate` 里没有停的条件——它数满步数就退出。

**但这是本项目第一次"有得停"。** 前两台机器的 `generate` 里同样没有 `break`，那可不是疏忽：字符级词表是 87 个字符，里面**没有"结束"这个符号**。`<`、`|`、`>` 三个字符在语料里只为分隔符而存在（各出现 2,387、4,774、2,387 次），而且要说一句"我讲完了"得**连续输出 13 个正确的 token**——没有单个符号能拿来当停的判据。

BPE 这边完全不同：`<|endoftext|>` 是**第 209 号，一个 token**。于是代码第一次有了可以停的地方：

```python
def generate(self, idx, max_new_tokens, temperature=1.0, eos_id=None):
    for _ in range(max_new_tokens):
        ...
        idx = torch.cat((idx, next_token), dim=1)
        if eos_id is not None and next_token.item() == eos_id:
            break                    # ← 唯一的改动
    return idx
```

**`eos_id` 默认 `None`，行为一字不变**——§7 那组对照（真词率 58.7% / 85.3% / 94.4%）因此继续成立，传 `eos_id=209` 才启用。脚本里两次生成并排打印（先不传，再传 209），实测第二次停在 **120 个 token**。

（真实实现里 batch 内每条序列结束时间不同，要用 `unfinished` 掩码逐条置位，不能整体 `break`；单条生成时 `break` 就够。）

### 8.1 它有多可靠：8 次采样实测

关掉 break、只记录"如果见到分隔符就停，会停在哪"，跑 8 次（温度 0.8，预算 500 token）。下表是**新生成的 token 数**：

| 第几次 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| 首次出现分隔符 | 219 | 213 | **27** | **24** | **9** | 273 | 389 | 331 |

**8 次全部出现（100%）**，位置跨度 **9 ~ 389，40 倍**。平均每次出现 2.1 个分隔符，而按语料密度（500 token ≈ 1,469 字符，每 838 字符一次）本该出现约 1.75 个——**频率是学准的**。

两个现象值得留意：

- **8 次全都停在 `\n` 后面。** 语料格式是 `...故事.\n<|endoftext|>\n...`，分隔符永远跟在换行之后——模型把这个也学进去了。
- **第 5 次只生成了 9 个 token**，补上开头就是一句完整通顺的 *"Once upon a time there was a little girl named Tim."* 也就是说，它在**一个开篇句之后**就认为一篇讲完了。8 次里有 3 次是这种极短输出（9 / 24 / 27 token）。

### 8.2 它省算力，但不兜底

首次出现位置跨度这么大，意味着**能不能停下来取决于你给多少预算**：

| 预算 | 20 token | 50 token | 200 token | 400 token | 500 token |
|---|---|---|---|---|---|
| 能停的比例 | 1/8 | 3/8 | 3/8 | 8/8 | 8/8 |

两面都要看：

- **省**：平均在 186 个 token 处就停了，同样的 500 预算**省掉约 60% 的算力**。
- **不兜底**：预算紧的时候 EOS 救不了你——200 token 时只有 3/8 能停。

而第 5 次那种 9 token 输出又说明另一头也需要保险。真实 API 因此还有第三个参数 `min_new_tokens`（"不许在 N 个 token 之前停"）。**上限 `max_new_tokens`、下限 `min_new_tokens`、模型自己说的 EOS——三个一起才完整**，而 EOS 是其中唯一一个"概率"，不是"保证"。

## 9. 回头看笔记 03 留下的那个问题

笔记 03 §6 列了四个暴露出来的问题，第 3 条是：

> **字符级的天花板**：语料里明明有 5,877 个词，模型却得一个字符一个字符地拼出来。

这一篇就是那条的答案。而且现在有数了：**同一个模型、同一份语料、同样的步数，只把「看世界的单位」从字符换成子词，每字符成本降 24%。**

**tokenizer 是模型看世界的眼镜**——这句话在这里第一次有了数字。

## 10. 下一步

笔记 03 的四个问题，现在剩三个：

| # | 问题 | 状态 |
|---|---|---|
| 1 | 数据加载：全份读进内存 | 没动 |
| 2 | 反馈周期：没有 checkpoint，断了全丢 | 没动 |
| 3 | ~~字符级天花板~~ | **这一篇解决了** |
| 4 | `block_size` 终于能用满 | 这一篇顺带解决了（50 token = 143.7 字符）|

剩下的 1、2 都是**工程问题**，不解决它们，后面每做一次实验都要交这份税（现在 6000 步已经要 4 分钟）。所以下一步建议：**补工程**——流式读数据、加 checkpoint、把 `eval` 和 `save` 分开。

分词器那边还剩一个可以调的旋钮：`N_MERGES` 现在是 500（词表 587）。调大到 2000 或者调小到 100，压缩率和词表代价会怎么换——这是一个**可以自己做的实验**。
