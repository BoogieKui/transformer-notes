# Tokenizer：从文本到 id 的那道桥

> 讨论源自 `mini_gpt.py` 的 §0（字符级 tokenizer），核心澄清一个问题：**tokenizer 和 word2vec 到底是不是一回事？** 不是——它们是一条流水线上紧挨着的两步。
>
> 交叉引用：词向量见 `notes/01-word-vectors/01-word2vec.md`，代码里的 tokenizer 见 `01-mini-gpt-reading.md` 的 §0。

---

## 1. Tokenizer 是干什么的

一句话：**把离散的文本符号，变成整数 id。** 计算机只认数字，文本是离散符号，必须有一座"符号 → 整数"的桥，这就是 tokenizer（分词器）。

```
"hotel motel cat ..."
   │  tokenizer
   ▼
[2731, 2732, 859, ...]      ← 整数 id，纯标号，无语义
```

## 2. 核心澄清：tokenizer ≠ word2vec

容易混，因为两者都"把词变成数字"。但一个是**编号**，一个是**赋义**：

| | tokenizer | word2vec / embedding |
|---|---|---|
| 做什么 | 符号 → 整数 id | id → 稠密向量 |
| 产物 | 标号（无语义）| 坐标（有语义）|
| 类比 | 发号码牌 | 在地图上找坐标 |

**用 word2vec 笔记的锚点对号：** 笔记里"给每个词一个唯一编号（hotel = 2731）"那一步，**就是 tokenizer**；后面的"把编号换成稠密向量、让 hotel ≈ motel 有相似度"才是 word2vec。所以 word2vec 不是"跳过"了 tokenizer——它自己就以 tokenizer 的输出为起点。

流水线：

```
text ──tokenizer──▶ [整数 id] ──embedding/word2vec──▶ [稠密向量]
        （标号）                 （语义）
```

## 3. 那为什么 word2vec "没提" tokenizer？

因为传统教材默认"词已经切好了"，把编号那一步一笔带过、没单独命名。到了现代 LLM（Large Language Model，大语言模型），**"怎么切 + 怎么编号"本身成了大事**，才被请上台面、单独立项。

## 4. 配套关系：tokenizer 是上游，word2vec 只是下游之一

tokenizer 产出的那串 id 是**通用格式**，谁都能接：

```
                  ┌─→ word2vec（学词向量）
text ──tokenizer──┼─→ GPT（学语言模型）        ← 同一个 tokenizer 喂给谁都行
                  └─→ RNN（循环神经网络）/ 分类器 / …
```

所以它不是 word2vec 的私配套，而是**所有文本模型共享的公共前端**。

## 5. "结果互相影响，实现彼此独立"

两个看似矛盾的结论，其实说的是两个层面：

**① 分词不同 → 学出的 word2vec 就不同**（结果依赖）。换"最小单元"，词表变了，向量表整个变了：

| 分词方式 | "hotel" 变成 | embedding 表里存的是 |
|---|---|---|
| 词级 | 1 个 token | 整个 "hotel" 一个向量 |
| 字符级 | 5 个 token | h、o、t、e、l 各一个向量 |
| 子词级（BPE，Byte Pair Encoding，字节对编码）| 2 个 token（hot + el）| "hot"、"el" 各一个向量 |

**② 代码解耦**（实现独立）。tokenizer 和下游模型只靠"整数 id"这个干净接口通信，换 tokenizer 不用改模型，换模型不用改 tokenizer。

一句话：**结果互相影响，实现彼此独立。** 类比：CPU 和内存是独立可替换的组件，只靠内存总线通信；但换不同规格的内存，系统性能当然会变。"整数 id" 就是那条内存总线。

## 6. 怎么选 tokenizer

所有取舍的根源在**一个核心权衡：词表大小 vs 序列长度**。

- 切得越粗（词级）：一个 token 信息越多，但词表越大、越容易撞到没见过的词。
- 切得越细（字符级）：词表越小、永不漏词，但序列越长。

而序列长度是致命的——注意力是 O(T²)。英文平均一个词 ≈ 4~5 个字符，纯字符级序列长度是词级的 **4~5 倍**，attention 成本放大 **16~25 倍**。

| 判据 | 词级 | 子词级（BPE）| 字符级 |
|---|---|---|---|
| 词表大小 | 巨大（几十万~上百万）| 可控（几万~十几万）| 极小（几十~几百）|
| 序列长度 | 短 | 中 | 最长（4~5×）|
| 未登录词（OOV）| 严重 | 几乎无 | 零 |
| 语义颗粒度 | 最粗 | 中（词根/词缀）| 最细 |
| 典型用途 | 经典 word2vec | GPT-2/3/4 | mini_gpt、教学 |

（OOV = out-of-vocabulary，未登录词。）

## 7. 每个选择是怎么"挣"来的

- **词级 = 历史起点**：简单、语义干净，但 OOV 致命（新词、错拼、专有名词全都塞进 `<UNK>` 或词表爆炸）。
- **字符级 = 最小可用**：词表极小（`mini_gpt.py` 用内置语料是 35，换 TinyStories 后 87）、零依赖、1500 步一两分钟跑完，但序列长、模型得自己学着把无意义的单字符拼成语义。mini_gpt 选它，因为现在付得起那 16 倍代价。
- **子词级（BPE）= 工程折中**：高频词整词保留、低频词拆成可复用的碎片，词表可控 + 几乎零 OOV + 保留词根词缀语义。BPE 本是 1994 年 Gage 的**数据压缩**算法，2016 年 Sennrich 等人搬到 NLP 做子词切分，GPT-2 起成 LLM 标配。

## 8. 决策规则

选 tokenizer 就是回答：**"词表代价"和"序列代价"，你更付得起哪个？**

- 付得起大词表（大 embedding、大 softmax、容忍 OOV）→ 词级
- 付得起长序列（O(T²) attention、长 KV cache）→ 字符级
- 两个都想省 → BPE（现代 LLM 的答案）

放在你的进度上：mini_gpt 选字符级是为了先"转起来"；等上下文变长、序列成了瓶颈，就该换 BPE 了。
